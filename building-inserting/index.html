Building and Inserting Interactives Into Projects

Interactive elements can enter a story in different ways. The right approach depends on where your story is built, what kind of interactive you are adding, and how much control the element needs.

Core idea: Start with the simplest method that does the job while allowing the control you need.

Choose the right path

Once you understand your purpose and pattern, select the tool that will allow you to complete your vision.

The four main ways to place an interactive

These methods can look similar inside your final story, but each path gives you different responsibilities.

Simple decision rule

Start with the lowest-responsibility option that still serves your story purpose.

Start simple
  1. If the builder has a good native block, use it. This is usually the easiest and most stable path.
  2. If a specialized tool does the job better, embed it. Use Datawrapper, Flourish, Genially, Knight Lab, or similar tools when they match the pattern.
  3. If you can't find a good external tool and the builder allows a small custom element, use a custom HTML snippet. Paste only the needed code, not a full HTML document.
  4. If the interactive needs full custom code, host it separately. Publish it with GitHub Pages and embed it with an iframe.

Native blocks

Native blocks are interactive elements already provided by the builder. This is usually the lowest-responsibility option when the built-in pattern is good enough for your story purpose.

Use the builder’s own feature first when it fits

If Shorthand, Tilda, Wix, WordPress, Squarespace, or another builder already has the pattern, test that before jumping to custom code.

Lowest friction

What you add

Add content inside the builder interface: text, photos, captions, labels, links, map points, timeline entries, or blocks.

What the builder handles

Most layout, hosting, responsive behavior, basic styling, and publishing.

What you still check

Check mobile layout, readable text, source notes, image quality, accessibility options, and whether the block actually serves your story purpose.

Limit: native blocks are convenient, but they can become tool-limited thinking. If the block cannot support the story purpose, move to an embedded builder or custom code path.

Native block workflow

This path should feel like building a page section, not coding a separate interactive.

Builder-first
  1. Choose the block that matches the job. Do not choose a block just because it looks interesting.
  2. Add the story content. Write the headline, instructions, labels, captions, and source notes.
  3. Adjust the visual settings. Match the page’s typography, spacing, color, and hierarchy as much as the builder allows.
  4. Test the mobile version. Builders often create mobile layouts automatically, but they still need checking.
  5. Ask whether the block is enough. If it cannot reveal, compare, locate, explain, or guide the way the story needs, use another path.

Embedded builders

Embedded builders are outside tools that create an interactive element and provide embed code. The embed code is usually an iframe, which places the external interactive inside the story page.

What embed code usually is

Tools like Datawrapper, Flourish, Genially, Knight Lab TimelineJS, and StoryMapJS often give you a block of code to copy. Most commonly, it contains an <iframe>.

Copy embed code
<iframe title="Where monarch butterflies migrate" src="https://www.example-embed-tool.com/my-interactive" width="100%" height="600" frameborder="0" scrolling="no"> </iframe>
In plain terms: the iframe is a window. The interactive lives somewhere else, and the story page displays it through that window.

Embedded builder workflow

Your main task is copying the correct embed code and placing it in a block that accepts embeds, custom HTML, or iframe code.

Iframe embed
  1. Build and publish the interactive in the external tool. The embed usually will not work if the chart, map, timeline, or graphic is still private or unpublished.
  2. Find the share or embed option. Look for buttons labeled Share, Embed, Publish, Add to website, or iframe.
  3. Copy the embed code. Copy the full code, not just the public URL, unless the builder specifically asks for a URL.
  4. Paste it into the story builder’s embed/custom code block. Use the block meant for embeds, not a normal text paragraph.
  5. Test the published story page. Make sure it loads, scales, and remains readable on mobile.

Common mistake

Pasting iframe code into a normal text block. The page may show the code as text instead of rendering the interactive.

Better approach

Use a block specifically labeled embed, HTML, custom code, iframe, or external content.

Embed checks

An embedded builder can make the technical build easier, but you still own how it works inside your story.

Before publishing

Check the tool

  • Is the interactive published or public?
  • Does the embed require a paid plan?
  • Does it show branding or a watermark?
  • Does it provide a responsive embed?
  • Does it include source notes and attribution?

Check the story page

  • Does it fit the page width?
  • Is the height tall enough?
  • Does it work on phone size?
  • Does it load in the published page?
  • Is there enough attendant text around it?

Custom HTML blocks

Some builders allow you to paste custom code into a page. This is different from creating a full standalone HTML file. In a custom HTML block, you usually need only the code for the element itself.

Use only the snippet, not the whole HTML document

A full HTML file has a wrapper around the page. A custom HTML block already lives inside another page, so do not usually paste the full wrapper.

Snippet only

Do not paste a full document into a block

<!doctype html> <html> <head> <title>My interactive</title> </head> <body> <div class="interactive">...</div> </body> </html>

Paste only the element code

<div class="interactive"> <button type="button">Show answer</button> <p hidden>This is the revealed explanation.</p> </div> <style> .interactive { padding:1rem; } </style> <script> // Small interaction script here </script>

Important: Some builders strip out <script> tags or require JavaScript to be placed in a separate settings area. You should test before assuming a custom block supports all code.

What to ask AI for

When you use AI to make custom code for a builder block, specify that they need a snippet, not a full page.

Prompt pattern
Make this as a copy/paste snippet for a custom HTML block. Do not include: - <!doctype html> - <html> - <head> - <body> Include: - the HTML for the element - the CSS inside a <style> tag - the JavaScript inside a <script> tag - comments showing where I can add more items - class names unlikely to conflict with the rest of the page
Class rule: if you are pasting into a custom HTML block inside a builder, the AI should produce a block-safe snippet unless the builder specifically asks for a full HTML document.

Custom HTML block checks

Custom snippets can be powerful, but they can also break because they live inside a larger platform page.

Responsibility rises

CSS conflicts

The builder page may already have styles. Use specific class names so the snippet does not accidentally restyle the whole page.

JavaScript limits

Some platforms block scripts, delay scripts, or require JavaScript in a separate footer/settings area.

Responsive behavior

A snippet that looks good inside a desktop block may overflow or become too small on mobile.

GitHub-hosted code

When your interactive is a full custom web page, you can host it on GitHub Pages and place it inside a story builder with an iframe.

When to host separately

GitHub-hosted code is useful when your interactive is too complex for a custom HTML block or when it needs its own files, folders, data, images, libraries, or JavaScript structure.

Standalone page

Good fit

  • Multi-file HTML/CSS/JS projects.
  • Interactive maps or visualizations with data files.
  • Projects that need their own layout and scripts.

Less good fit

  • Very small reveal elements that could be native blocks.
  • Projects with giant unoptimized media files.
  • Anything that has not been tested at iframe size.

GitHub iframe workflow

Your final story page does not contain all the code. It contains an iframe that points to the separately published GitHub Pages URL.

Hosted embed
  1. Build the interactive as its own web page. The project should have an index.html file and any needed CSS, JavaScript, image, or data folders.
  2. Publish the project with GitHub Pages. Confirm that the public GitHub Pages URL loads correctly by itself.
  3. Copy the live GitHub Pages URL. Do not use the repository URL. Use the published page URL.
  4. Put that URL inside an iframe. Paste the iframe into the story builder’s embed/custom code block.
  5. Adjust the iframe height. The iframe often needs a fixed height so the full interactive is visible.
  6. Test the final story page. Check desktop, phone width, links, scrolling, and loading.
<iframe title="Interactive bird migration explorer" src="https://username.github.io/project-name/" width="100%" height="700" style="border:0;" loading="lazy"> </iframe>

Repository URL vs. published URL

It is easy to copy the wrong URL. The GitHub repository is where the code lives. GitHub Pages is where the finished page lives.

Common confusion

Wrong for iframe

https://github.com/username/project-name

This is the code repository. It is not the published interactive page.

Correct for iframe

https://username.github.io/project-name/

This is the public GitHub Pages URL that can be embedded.

Testing before publishing

Getting the interactive into the page is not finished until you test it inside your final story environment.

Final placement checklist

These checks apply to native blocks, embedded tools, custom snippets, and GitHub-hosted iframes.

Quality control

Interaction checks

  • Can users tell what to click, tap, drag, scroll, or select?
  • Does the interaction work after the full story page is published?
  • Does it work with touch, not just mouse hover?
  • Are buttons and links actually clickable?
  • Does the reader get a clear result from interacting?

Production checks

  • Does it fit the page width?
  • Is the height tall enough?
  • Does it work on mobile?
  • Are media files optimized?
  • Are sources, credits, and AI disclosures included where needed?

Common problems

Most embedding problems come from the wrong block type, the wrong URL, missing publication settings, file paths, or iframe sizing.
